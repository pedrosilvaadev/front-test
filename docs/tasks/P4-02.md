## Decisions / contract interpretations
- **Pagamento form = buyer + wallet:** the Figma form fields are the order `buyer` and the `WalletInput` of the paying wallet (one form, filled once). On submit:
  1. `PUT /api/wallets/:slot`, only when the values differ from the saved wallet.
  2. `POST /api/wallets/:slot/connection`, when the wallet is not connected.
  3. `POST /api/orders`.
- **Wallet slots:** "Usar outra carteira?" (desktop) and the mobile "Carteira conectada" cards select the slot (`primary`/`secondary`) and prefill from the saved wallet. Wallet label defaults to Principal/Reserva.
- **Provider choice:** the "Carteira e rede" radios are the wallet `provider`. The duplicate "Tipo de carteira" select from the desktop frame is not rendered (same value).
- **ENS:** entered without the suffix; `.eth` is shown as a fixed suffix (Figma ".eth ▾").
- **Seeded wallets:** `src/mocks/fixtures/wallets.ts`. The collector has a primary Ethereum/MetaMask wallet and a secondary Polygon/Coinbase one, both disconnected. The creator has none.
- **Mock db:** `DB_SCHEMA_VERSION` 4 → 5 (`wallets`, `orders`, `checkoutControls`). New `src/mocks/wallet-store.ts` (not in the ownership list; mock-only).
- **Orders mock (`src/mocks/order-store.ts`):**
  - The idempotency fingerprint is canonical JSON with sorted keys, scoped per user and checked before any revalidation.
  - An order buys exactly the quote lines.
  - Revalidation compares the quote lines with the current catalog, coupon and fee:
    - any price/coupon/fee change → `QUOTE_CHANGED`;
    - a line no longer fulfillable → `AVAILABILITY_CONFLICT`;
    - in both cases `details` is `{ changes, quote }` with a fresh quote.
  - Stock is reserved at creation and released on decline. On confirmation the purchased quantities are removed from the user cart (cart `version` bump).
  - An empty quote → 422 `VALIDATION_ERROR` (contract gap: receipts need ≥ 1 line).
  - Order id is `ord_<hex>`. Explorer URLs: etherscan.io, polygonscan.com, solscan.io.
- **Client idempotency (`src/features/checkout/place-order.ts`):**
  - Same payload: replay the persisted attempt (or read its order).
  - Different payload: first resolve the previous attempt. A still-pending order is returned instead of paying again; a terminal or rejected attempt is cleared.
  - Only then is a new UUID key created, persisted before the POST.
  - Network/timeout errors keep the attempt. Revalidation errors (`QUOTE_*`, `AVAILABILITY_CONFLICT`, `WALLET_*`, 422, `IDEMPOTENCY_CONFLICT`) clear it.
  - The order page clears the attempt once its order is terminal.
- **Session manager:** explicit logout (and a logout in another tab) clears the user's attempt and the `sessionStorage` draft. Sign-in, including another tab's sign-in, clears other users' attempts and drafts. Expiry keeps both.
- **Re-confirmation:** a quote that reports `changes[]`, a 409 `QUOTE_CHANGED`/`AVAILABILITY_CONFLICT` (the fresh quote goes into the cache), or `QUOTE_EXPIRED` shows a review box. "Confirmar compra" stays disabled until "Aceitar novos valores" is clicked. The new quote means a new payload, so a new key.
- **Order page:** `/pedidos/$orderId` (`_authed`). It polls `GET /api/orders/:id` while pending with backoff (1 s, 2 s, 4 s, then 5 s). The receipt is rendered only from `order.receipt` and only when confirmed. Declined → reason, plus "Tentar novamente" (`/checkout`) and "Voltar ao carrinho". Terminal states invalidate the cart and catalog caches.
- **Cart page:** "Conectar e finalizar" now links to `/checkout` (disabled while the quote is not purchasable). Guests go through login and come back with their cart merged.
